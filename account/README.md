# Isolated account broker

This additive Worker is a generic central-account OAuth/read broker. It does not run the existing installation-token MCP service and imports nothing from `src/`. The existing service's no-provider-token-storage and no-content-proxy promises do not describe this separate Worker: this broker keeps encrypted per-person GitHub OAuth credentials server-side and performs constrained repository reads itself.

**Private activation is disabled.** The supplied Wrangler file has reserved synthetic URLs, no live client ID, signing key, vault key or connector namespace. No login, registration, grant, deployment or actual account linkage has been performed. A dry bundle is not a deployment.

## Central-account contract

No deployed central-account identity issuer is established by this source. The approved account-owned identity authority described below supplies a verified account assertion or `__Host-account_assertion` secure HttpOnly SameSite=Lax cookie, signed ES256 by the configured account issuer. It must contain `sub`, numeric `github_id`, exact `service` and `resource`, positive `grant_generation`, single exact audience, and `iat`/`exp` no more than five minutes apart. Initial account generation is 1. Identity linking by email or mutable login is forbidden. The account-owned browser routes below establish numeric identity and bounded sessions; existing service assertion validation remains unchanged.

The public browser calls CSRF-checked POST `/account/repositories/connect`. Raw public `/oauth/start` and cookie-less `/oauth/callback` are denied even with a valid connector/account assertion. The browser wrapper alone supplies trusted browser context to the binding-only broker OAuth methods. Those methods use maintained-library state/S256, exact callback, numeric identity and exact scope/expiry evidence. Identity bootstrap is separately `/account/signin` → `/account/callback`; it does not call the old already-authenticated identity broker seam. A single pending broker transaction per subject bounds retained state; expired state cannot be exchanged.

Public POST `/authorize` is a CSRF-checked browser form, not an assertion-only JSON API. Cookie-less POST denies without calling the internal completion helper. Registered client, exact redirect/resource and only `repository:read` are checked; NEW consent requires a current repository grant plus a local browser identity verified within five minutes. Initial or stale-session authorization now stores bounded encrypted original intent and resumes it through fixed `/account/continue` after identity and any separately required repository consent. Client state, registered redirect and S256 challenge are preserved; each rendered form binds its exact opaque continuation reference. No dynamic client-registration endpoint is enabled. The maintained provider serves `/token` and OAuth metadata.

Repository provider exchange prepares one encrypted, unusable candidate per subject; it does not replace the current grant. The encrypted candidate binds random one-use ID, subject, GitHub numeric ID, exact browser handle/generation/account epoch, expected grant state/generation and five-minute post-preparation expiry. Raw handle and credentials never appear in candidate plaintext storage. A replaced ID cannot delete the newer candidate. Final browser-authority `blockConcurrencyWhile` validates active identity, exact epochs and five-minute freshness before the internal grant commit. Candidate consume and grant CAS share one grant-storage transaction. No provider network I/O occurs under the browser event gate. NEW connector completion uses maintained `getOAuthApi` and the same final browser event gate through KV authorization persistence. Existing connector renewal is unchanged.

The gate linearizes final authorization against local signout/revoke-all; it is not a distributed transaction or rollback guarantee. Signout that wins during provider exchange prevents candidate commit and leaves the old grant unchanged. If commit wins, later local signout intentionally does not disconnect that established grant. Cloudflare's event gate has a 30-second reset timeout; caught errors remain denied without deliberately resetting the authority. An interrupted commit response is an unknown outcome, so the UI directs checking account state instead of falsely stating no access was granted. An unconsumed candidate is encrypted, unusable after expiry, and replaced by the next preparation; production retention/cleanup remains an activation obligation. Maintained-provider partial KV failure recovery/retention remains an operational gate, not a local rollback claim.

A consuming service sends the native opaque token plus its separate signed service assertion to POST `/connector/session`. The broker locally routes verification to the single configured resource URL; no network proxy or caller-selected URL is involved. This lets the provider enforce its real request-URL audience semantics without weakening exact-resource validation. Verified provider props contain safe identity/generation references only. The result is a five-minute account assertion, generation and expiry. The service then POSTs `/read` using that assertion and its own service assertion. `/session/renew` also supports already signed account assertions.

Refresh generations stay within an explicit consent epoch. Disconnect invalidates the epoch; an old connector token cannot renew after reconnect. Reconnect needs an independently authenticated account assertion at the current disconnected generation. The account owner maintains that state; an old native token cannot self-upgrade it.

## Native fetch invocation regression

`tests/native-access/native-fetch-receiver.test.ts` is part of `npm test`. It bundles the actual `GitHubReads`, `GitHubOAuth` and broker guard into installed local workerd, supplies the original native `fetch` at their production constructor seams, and leaves the Worker global unchanged. A network-disabled synthetic dispatcher sits outside the Worker boundary. Its bridge returns redirect responses verbatim so the native Worker exercises the production policy; the bridge never follows a redirect itself.

Both receiving constructors preserve the supplied transport through a lexical adapter, avoiding a native fetch invocation with the class instance as receiver. For OAuth requests explicitly using `redirect: error`, the adapter uses workerd-supported `manual` and cancels and rejects every 3xx response body before parsing or disclosing it. Existing explicit-manual callers keep their existing redirect handling; archive allowlists and credential boundaries are unchanged. Maintained OAuth4WebAPI code/refresh calls and numeric `/user` verification use this same receiver-safe transport.

The regression first reproduced `Illegal invocation` with the original constructors. Constructor-only repair then exposed workerd's unsupported `redirect: error` on `/user`; the no-follow adapter repaired that separate runtime mismatch. Tests now exercise fixed reads, code exchange, refresh, numeric identity/scope denials, forbidden operations, rejected archive destinations and provider-token output denial. OAuth token and identity responses with 301, 302, 303, 307 and 308 are denied with zero dispatch to the second destination and no synthetic credential/body/header output. The existing host persistence tests use a global synthetic fetch adapter and therefore could not prove this receiver property; this separate test closes that evidence gap.

This is synthetic native-runtime evidence at compatibility date `2026-06-16`. It does not establish real GitHub OAuth behavior or production-date compatibility and does not authorize activation.
