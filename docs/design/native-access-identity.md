# Native account identity and read boundary

Status: isolated source candidate; private activation disabled. This design applies only to `account/`, a separate generic Worker, not the existing installation-mint runtime.

A configured central-account issuer authenticates a stable subject and verified numeric GitHub ID. A distinct service issuer authenticates the calling service. Both asymmetric ES256 assertions must have the exact audience, resource and service. The broker never accepts decode-only JWTs or a service credential as authority to choose a person's grant.

GitHub classic OAuth `repo` is broad upstream authority, including writes across accessible repositories. This service exposes only five read actions; calling it read-only does not narrow the GitHub grant. Repository code grants must return exactly the expected normalized `repo` scope both at the token response and `/user` scope header, with positive access/refresh expiry and a rotating refresh token. Identity-only sign-in requires exactly `read:user` and cannot persist a repository grant. Any other behavior denies the affected operation. Actual GitHub.com behavior is a separate unrun provider gate, not established by intercepted responses.

The maintained OAuth4WebAPI adapter owns state/PKCE/code/refresh protocol operations. Subject-sharded Durable Objects retain one pending expiring transaction and a JWE encrypted credential envelope. JOSE A256GCM binds subject and generation inside the encrypted envelope. Atomic compare-and-swap handles rotation; a process's single-flight prevents concurrent refresh replay. An uncertain refresh state cannot reuse its old token. Disconnect wins against stale refresh completion.

Grant `generation` changes on credential rotation; `epoch` changes on grant replacement or revocation. Renewal can advance assertions only inside their original epoch. This distinction prevents a retired connector token from reconnecting itself while allowing legitimate refresh lineage. Signed account assertions from the owned account are required for a new consent epoch.

`BrokerReadRequest` has request ID, exact resource/action, owner/name, optional canonical ID only for `resolve_repository`, and optional ref/SHA/path. Every operation performs fresh authorized provider repository metadata lookup before data access; supplied IDs must match. Default-branch resolution obtains a full commit SHA, including non-main branches. Subsequent tree/blob/archive operations are pinned to that snapshot. No arbitrary URL, method, headers or unknown request keys are accepted. All other actions require numeric repository ID.

The response binds subject, numeric GitHub ID, service, exact resource/action, canonical repository ID, generation, decision/request IDs, metadata-check time, snapshot SHA and exact intent. A generation check immediately before response suppresses disconnect races. No positive authorization cache exists. Immutable snapshot identity is evidence, not future authorization.

Archive redirects are limited to the exact owner/repository/commit codeload path derived from the authorized request. Provider Authorization never crosses origins. Streaming size limits bound compressed data; downstream archive expansion/path extraction and every persisted disclosure remain separate consumer obligations. Blob responses must be files at the exact requested path, with base64 content and full blob SHA; tree truncation/path traversal denies. Credential echoes in wire data, including base64 payloads, deny.

The native connector uses Workers OAuth Provider 0.7.2 with exact resource matching and safe props. `/connector/session` is a fixed transport alias internally rewritten to the configured resource for the provider's actual request-URL audience check; no remote fetch or arbitrary routing results. That protected handler issues a current-generation short assertion only after separate service verification. Registered-client consent is explicit and authenticated; no new dynamic registration endpoint is enabled.

Synthetic tests cover two users and three owner-qualified same-name repositories, scope inheritance, callbacks/identity/PKCE/state replay, refresh races, revocation, confused deputy inputs, no credential payload, actual maintained native OAuth token exchange and resource rejection. Live account UI, provider, cloud persistence and consumer caching remain separate activation/validation gates.

Learning: (1) a single monotonically increasing generation cannot distinguish token refresh from reconnect—use and test consent lineage; (2) a protocol helper passing in isolation cannot prove a native opaque-token chain—exercise actual provider token and request-URL semantics; (3) cold owner/name discovery must derive numeric IDs rather than require IDs that only fixture authors already know.
